# Скользящее среднее и декомпозиция временного ряда

**Тема:** Сглаживание, выделение тренда и сезонности.

**Датасет:** **Store Sales — Time Series Forecasting** (Kaggle).  
Ссылка: `https://www.kaggle.com/competitions/store-sales-time-series-forecasting`  
Этот датасет содержит ежедневные продажи сети магазинов (Favorita) с 2013 по 2017 год, а также информацию о праздниках, ценах на нефть и транзакциях. Он широко используется в учебных проектах для анализа временных рядов.

**Что сделать (только аналитическая часть, без ARIMA):**

- Агрегировать данные до дневного или недельного уровня по всей сети или по отдельным магазинам.
- Построить **простое скользящее среднее** (окно 7, 14, 30 дней) и **экспоненциальное скользящее среднее** для сглаживания шума.
- Провести **STL-декомпозицию** (тренд + сезонность + остаток) для одного-двух магазинов.
- Визуализировать компоненты и сделать вывод: когда наблюдается сезонный пик, есть ли долгосрочный тренд.
- В README объяснить, чем отличается аддитивная модель от мультипликативной и почему выбрана конкретная.

**Почему это аналитический проект:** Ты работаешь с описанием уже случившегося, а не прогнозируешь будущее. Это типичная задача при подготовке ежемесячных отчётов: «покажи тренд без недельного шума».

## Зафиксированные решения (Q&A, 2026-09-23)

1. **Структура и git:** зеркалим референс (`new18`): `src/`, `tests/`, `notebooks/` со `build_*.py`, `reports/`, `assets/`, `notes/`, `data/README.md`. `git init` прямо в `/mnt/d/opencode/new23`, ветка `main`, работаем в этом каталоге напрямую (как в референсе).
2. **Язык:** код и итоговые артефакты — английский (`README.md` EN + `README_ru.md` RU); `notes/` — русский; объяснения в чате — русский с англ. терминами.
3. **Агрегация:** дневная по всей сети (сумма продаж всех магазинов и семей) — основной ряд. Для магазинов из STL — тоже дневной. MA-окна 7/14/30 осмысленны только на дневном ряду.
4. **Магазины для STL:** два разнотипных — крупнейший типа `A` (по сумме продаж за весь период) и малый типа `D`/`E`. Правило выбора — детерминированная функция в `src/eda.py` (`pick_stl_stores`), один источник правды для ноутбуков 01 и 03.
5. **Праздники:** `holidays_events.csv` используется, но только национальные праздники (`locale == "National"`) как аннотации к пикам. `oil.csv`, `transactions.csv`, `test`/`sample_submission` не используются (вне плана).
6. **Тесты:** pytest покрывает расчётную логику `src/`: сверка MA/EMA с pandas, STL со statsmodels, коммутативные/структурные проверки; честные допуски (`pytest.approx(rel=...)`).
7. **Отчёт:** итоговый HTML (`reports/04_executive_summary.html`) через `nbconvert` из ноутбука 04.
8. **Стек/окружение:** Python 3.12.3 (system) + `uv`; изолированный `.venv` в new23; `requirements.txt` с закреплёнными версиями.
9. **Данные не коммитим:** `data/*.csv` в `.gitignore` (train.csv ~122 MB); источник и схему документирует `data/README.md`.
10. **Без ARIMA/ML:** только описательный анализ (сглаживание + декомпозиция). `random_state` не требуется (нет случайности), всё детерминировано.
11. **STL-период:** weekly seasonality, `period=7`.
12. **Роль магазинов в README:** аддитивная vs мультипликативная модель — обе реализуются (мультипликативная через STL на `log`), выбор подтверждается числами (сила сезонности, остатки); README объясняет разницу и причину выбора.

## Task 1 — Data integrity & EDA

**Цель:** проверить целостность `train.csv` до любых выводов; выбрать магазины для STL; дать описательную картину (единый дневной ряд сети, профиль по дням недели, топ магазинов, роль промо).

**Файлы и контракты:**

- `src/__init__.py` (пустой).
- `src/eda.py` — функции с докстрингами:
  - `load_train(path) -> pd.DataFrame` — загрузка с типами: `id` int64, `date` datetime64, `store_nbr` int16, `family` category, `sales` float32, `onpromotion` int32. Оптимизированное чтение 122 MB.
  - `integrity_report(df) -> dict` — строки, диапазон дат, число магазинов/семейств, дубликаты `(date, store_nbr, family)`, пропуски по колонкам, `sales` min/max/доля нулевых, `onpromotion` min/max, непрерывность календарной сетки (дни, отсутствующие в `date`).
  - `assert_integrity(df) -> None` — жёсткая проверка: `ValueError` при дубликатах, пропусках, отрицательных `sales`, разрывах календаря.
  - `daily_network_sales(df) -> pd.Series` — сумма продаж по всем магазинам и семьям на дату, отсортирована по дате, индекс ежедневный.
  - `store_daily_sales(df, store_nbr) -> pd.Series` — дневной ряд конкретного магазина.
  - `store_type(df, store_nbr) -> str` — тип магазина.

  - `promotion_share(df) -> pd.Series` — доля строк с `onpromotion > 0` по датам (для EDA-графика сырой видимости промо-активности).
- `tests/test_eda.py` — фикстура-синтетика, зеркалящая схему Kaggle (малые данные вручную); покрыть: типы после `load_train`, агрегация `daily_network_sales` на ручной мини-таблице (суммы известны вручную), дубликаты/пропуски/отрицательные/разрывы ловятся `assert_integrity`, `pick_stl_stores` на мини-таблице с `A` и `D/E`, `promotion_share` ∈ [0,1]. ## Task 2 — Smoothing: MA и EMA

**Цель:** сгладить недельный/ховой шум дневного ряда сети; показать и сравнить SMA (7/14/30) и EMA; зафиксировать, что видно «без шума».

**Файлы и контракты:**

- `src/smoothing.py`:
  - `simple_moving_average(series: pd.Series, window: int, center: bool = False) -> pd.Series` — скользящее среднее с обработкой краёв (NaN там, где окно неполное), опция центрирования; докстринг: зачем именно этот способ (порядок окна = период сглаживания).
  - `exponential_moving_average(series: pd.Series, span: int) -> pd.Series` — `ewm(span=span, min_periods=span)`; докстринг: `span` vs `alpha` (alpha = 2/(span+1)), почему EMA не имеет NaN-краёв, но «отстаёт».
  - `mae_smoothing` не нужно; **не добавлять** функции, которых нет в задаче.
- `tests/test_smoothing.py` — MA на константном/треугольном ряду = ручная свёртка в валидных точках (rel-допуск); NaN на краях; центрированная vs хвостовая; EMA совпадает с ручным экспоненциальным взвешиванием для малого ряда; сверка с pandas — через точность float (`rel=1e-9`), причина допусков — в комментариях тестов.
- `notebooks/build_02_smoothing.py` → `notebooks/02_smoothing.ipynb`: сырой ряд vs MA7/14/30 (вывод: что окно 7 убирает недельность, 30 — месячный уровень); сырой ряд vs EMA (span 7/30); сравнение MA7 vs EMA7 на одном графике (лаг EMA); вывод, какой взгляд отвечает на вопрос «тренд без недельного шума».
- `assets/smoothing_ma.png`, `assets/smoothing_ema.png`, `assets/smoothing_ma_vs_ema.png`.
- `notes/02_smoothing.md`.

**Критерий приёмки:** pytest зелёный; ноутбук без ошибок; графики отвечают на вопросы; в notes/02 разобрано «почему MA окна дают либо запаздывание, либо сглаживание», pitfalls (края, лаг EMA, выбор span).

## Task 3 — STL-декомпозиция и праздники

**Цель:** разложить ряд сети и два магазина на тренд + сезонность + остаток; объяснить пики национальными праздниками; обосновать аддитивную vs мультипликативную модель числами.

**Файлы и контракты:**

- `src/decomposition.py`:
  - `stl_decompose(series: pd.Series, period: int = 7, robust: bool = True) -> pd.DataFrame` — обёртка над `statsmodels.tsa.seasonal.STL` (докстринг: почему STL, почему `period=7`, почему `robust`; возвращает DataFrame с колонками `trend`, `seasonal`, `resid`; проверка серии на непрерывность и длину ≥ 2*period+1).
  - `seasonality_strength(components: pd.DataFrame) -> float` — F_s = max(0, 1 - var(resid)/var(resid+seasonal)) (Wang, Smith & Hyndman 2006); докстринг с формулой.
  - `trend_strength(components: pd.DataFrame) -> float` — F_t = max(0, 1 - var(resid)/var(resid+trend)).
  - `decompose_additive_vs_multiplicative(series: pd.Series, period: int = 7) -> dict` — аддитивная (STL на исходной шкале) и мультипликативная прокси (STL на `log`, компоненты `exp`-преобразуются назад для сопоставимости сезонности); возвращает dict с компонентами обеих моделей + `seasonality_strength`/`trend_strength` и относительный `resid_relative_std` каждой — это данные для выбора модели в README.
  - `national_holidays(holidays_path: str, start: str, end: str) -> pd.DataFrame` — подмножество `holidays_events.csv` с `locale == "National"` в диапазоне дат; колонки `date`, `description`.
- `tests/test_decomposition.py` — синтетический сезонный ряд: сезонная компонента ловит период, сумма trend+seasonal+resid ≈ исходный ряд (rel=1e-6), `seasonality_strength`/`trend_strength` ∈ [0,1] и на выраженной сезонности F_s близка к высоким значениям; `national_holidays` фильтрует только National и только диапазон; `decompose_additive_vs_multiplicative` возвращает все ключи, значения согласованы.
- `notebooks/build_03_stl.py` → `notebooks/03_stl_decomposition.ipynb`: STL сети (4-панельный график); STL двух магазинов; сезонная компонента сети с аннотацией национальных праздников (вертикальные линии Рождества/НГ, Пасхи, национальных дат); таблица силы сезонности и тренда; сравнение аддитивной и мультипликативной (таблица + график) и зафиксированный выбор модели с обоснованием.
- `assets/stl_network.png`, `assets/stl_store_a.png`, `assets/stl_store_small.png`, `assets/seasonal_peaks_holidays.png`, `assets/additive_vs_multiplicative.png`.
- `notes/03_stl_decomposition.md`.

**Критерий приёмки:** pytest зелёный; ноутбук без ошибок; пики идентифицированы и сопоставлены с праздниками; выбор аддитив/мультипликатив подтверждён числами и записан в notes/03.
