# Заметки — Этап 5: README (EN/RU) и definition of done

## Цель

- Написать `README.md` (английский) и `README_ru.md` (русское зеркало) по
  структуре «Ultimate README Guide»: заголовок с таглайном, честные бейджи,
  баннер-график, TOC, Introduction в рамке «ежемесячного отчёта», Tech Stack,
  Project Structure, Quick Start, Data, EDA, Methodology, Results, Testing,
  Limitations, Recommendations, Support, Contributing, License,
  Acknowledgements, а также раздел Learning Resources (учебная рамка проекта).
- Провести финальную сверку всех артефактов (definition of done): git чист,
  pytest 56/56 зелёный, ноутбуки пересобираются детерминированно, каждый PNG
  из README существует в `assets/`, вердикты совпадают в README EN/RU,
  ноутбуке 04 и HTML-отчёте, badge-числа соответствуют реальности, приватные
  файлы не коммитятся.

## Зачем это важно

1. **README — единственная точка правды для читателя.** Ноутбуки 01–04 —
   рабочие артефакты; README собирает историю в один документ, который
   читают первым. Если README врёт (бейдж «100 тестов», график, которого
   нет в `assets/`, невыполнимый Quick Start) — дискредитирован весь проект,
   включая честные цифры внутри.
2. **Вердикт — один и тот же во всех носителях.** Читатель может проверить
   вывод по трём местам: README (EN/RU), ноутбук 04, HTML-отчёт. Любое
   расхождение формулировок трактуется как противоречие и подрывает доверие
   сильнее, чем «скучный» вердикт. Поэтому заголовочные предложения вердикта
   дословно процитированы из исполненного ноутбука 04.
3. **Definition of done — гарантия, что проект закончен.** DoD-список
   превращает «вроде всё готово» в проверяемые команды с выходами: `git
   status` чист, `pytest` зелёный, повторная пересборка не даёт диффа,
   каждая картинка существует, приватные инструкции не попали в git.
4. **Badge-числа — это утверждения, а не украшения.** Бейдж «56 passing»
   обязан совпадать с реальным прогоном pytest; бейдж версии Python — с
   фактической версией. Культурно это то же правило, что
   number-must-be-code, только на уровне метаданных репозитория.

## Ключевые термины (с английским эквивалентом)

- **Definition of done / DoD** — чек-лист «проект завершён»: не «мы сделали
  фичу», а «вот команды и их выходы, которые это доказывают».
- **README-vs-reality drift** — тихий дрейф документа от реальности:
  бейджи/графики/команды перестали соответствовать коду; чтобы его ловить,
  каждая картинка проверяется на существование, каждый бейдж — на источник.
- **Verdict consistency** — согласованность вердикта: одинаковые
  заголовочные фразы в EN/RU README, ноутбуке 04 и HTML-отчёте (один
  «источник правды» — исполненный ноутбук, остальные цитируют его).
- **Banner figure** — «обложка» README: один график, который сразу отвечает
  на главный вопрос проекта (здесь — STL-декомпозиция сети: тренд +
  недельная сезонность).
- **Badge honesty** — честность бейджей: числа на шильдиках равны числам из
  выполняемых команд, не «желаемым» значениям.
- **Mirror translation** — зеркальный перевод: README_ru.md повторяет
  структуру и порядок секций README.md, а не вольный пересказ.

  буквы задания.

## Подводные камни

1. **README-vs-reality drift — главный убийца портфолио.** Три источника
   дрейфа, каждый пойман в этом этапе: (а) бейджи — «56 passing» проверяется
   реальным прогоном, а не переписыванием из старой сборки; (б) имена
   ассетов — в задании были `smoothing_ema_weekly.png` и
   `smoothing_ema_monthly.png`, реальные файлы называются `smoothing_ema.png`
   и `smoothing_ma_vs_ema.png`, и README должен ссылаться на существующие, а
   не «планировавшиеся»; (в) Quick Start — команда должна выполняться
   буквально (build-скрипты запускаются из `notebooks/`, экспорт HTML — из
   корня, pytest — из корня), иначе читатель ловит ошибку «команда не
   работает».
2. **Вердикт обязан быть идентичным везде, и источник — один.** Нельзя
   «по-разному пересказать» одну находку в README и ноутбуке: формулировки
   сверялись дословно с исполненной ячейкой §5 ноутбука 04 (а она, в свою
   очередь, цитирует только напечатанные кодом числа — number-must-be-code).
3. **Приватные файлы в коммите — самая дорогая ошибка финализации.**
   `AGENTS.md`, «Ultimate README Guide.md» и CSV-данные исключены из git:
   правило — `git add -n .` → ревью → `git check-ignore` на каждый приватный
   путь, потом реальный `git add`.
4. **HTML-отчёт — производный артефакт и должен соответствовать
   закоммиченному ноутбуку.** Поэтому порядок финальных шагов фиксирован:
   пересборка ноутбуков → проверка, что git чист → экспорт HTML → повторная
   пересборка → git снова чист (детерминизм). Экспорт раньше финальной
   стабильной пересборки дал бы рассинхрон репозитория и отчёта.
5. **Near-tie продавать нельзя.** В README строка «выбран multiplicative»
   немедленно сопровождается оговоркой «0.94%, практически ничья, тест не
   запускался» — иначе это подгонка под красивый вердикт.
6. **Графики в README — не декорация, а ответ на вопрос.** Каждая картинка
   привязана к своему утверждению (тренировочный график в EDA, недельный
   профиль в Results, сравнение моделей в Results); дублирующих графиков
   нет, неиспользованные ассеты остаются только в ноутбуках.

## Запуск

```bash
# тесты (база перед всем остальным)
.venv/bin/python -m pytest tests/ -q

# пересборка всех ноутбуков (must be byte-identical при повторе)
cd notebooks && for b in build_01_eda build_02_smoothing build_03_stl build_04_summary; do ../.venv/bin/python "$b.py"; done

# экспорт HTML
../.venv/bin/python -m jupyter nbconvert --to html --output-dir ../reports 04_executive_summary.ipynb

# контроль приватных файлов перед push
git add -n . && git status --short
git check-ignore AGENTS.md "The Ultimate README Guide.md" .venv data/*.csv
```
